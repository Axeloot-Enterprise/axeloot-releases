
### Added
- **Durable staged agent software release governance** now gates enrolled-agent
  package offers through database-backed campaigns across Pilot, IT, Early
  Adopters, Production, and Critical Systems. Operators can preview scoped
  targets, verify compatibility/readiness, start and advance one ring at a time,
  pause/resume, pin signed versions, cancel unreleased work, and request an exact
  signed rollback with endpoint-reported success evidence. Duplicate release
  actions are idempotent at the database boundary, and the existing Updates
  Settings surface now distinguishes unavailable data from real zero counts.
  (risk: critical — new durable release schema and fail-closed agent update gate)
  - Migration: automatic `v13.7-agent-release-*` tables/indexes plus
    `v13.7-agent-command-release-action-key`; no existing deployment JSON is
    imported because it was not an authoritative concurrent-safe campaign log.
  - Agent rollout: publish agent 5.1.3 so endpoints report update protocol,
    policy-signature protocol, and package-format capabilities; older agents are
    classified as unknown when a package declares those requirements.
  - Rollback: restore the pre-deploy database backup and previous server/agent
    images, or ship an approved forward migration; never delete migration-history
    rows. A campaign rollback itself requires a real previous signed package and
    reports queued, pending, succeeded, and failed endpoint evidence.
  - Evidence limit: automated server, agent, migration, and UI checks cover the
    software contract; owner physical-endpoint and production validation remain
    pending.
- **Air-gapped delivery is now the primary distribution channel.**
  `deploy/linux/build-bundle.sh` packs all three images (application, PostgreSQL,
  Redis) plus the whole deployment set; `install.sh` / `upgrade.sh` take
  `--image-archive` and never contact a registry. Proven end to end: a real
  v5.8.0 bundle was installed on an isolated daemon with zero images where
  `docker pull` failed with *network is unreachable*, and PostgreSQL and Redis
  reached healthy in 10s. (risk: low — additive; the registry path is unchanged)
- **`deploy/linux/init-secrets.sh`** generates the secret material a first
  install needs: the two 32+ character passwords, a private CA and a PostgreSQL
  server certificate carrying `SAN DNS:postgres`, and `config/app.env` with fresh
  `SECRET_KEY` / `ENROLLMENT_TOKEN_SALT` / `AGENT_SECRET`. It verifies its own
  certificate against the name before installing it and **never regenerates**,
  because rewriting a password or CA under a running deployment would lock it out
  of its own database.
- **`scripts/release/release_completeness.py`** — a cut tag that distributes
  nothing now fails loudly. Checks the tag, the GitHub Release and the image, and
  asserts the **provenance chain**: the image's
  `org.opencontainers.image.revision` must be the commit the tag points at.

### Fixed
- **Settings operational integrations now share secure, explicit contracts.** SMTP delivery,
  retries, and draft connection tests use the canonical `smtp_user` key and certificate-verifying
  implicit TLS/STARTTLS without plaintext downgrade; LDAP automatic sync is explicitly enabled
  and missing-user deactivation is opt-in and fail-closed; credential-bearing webhook URLs are
  write-only in Settings and excluded from notification history, logs, audit details, and
  diagnostics. (risk: high — worker delivery and directory lifecycle safety change)
  - Migration: none required. Existing `smtp_username` rows remain a read-only compatibility
    fallback; `ldap_deactivate_missing_users` defaults to `false` when absent.
  - Rollback: revert the change and redeploy. Before rollback, keep automatic LDAP sync disabled
    unless the former implicit missing-user deactivation behavior is explicitly acceptable.
  - Affected endpoints: `GET/PUT /api/settings`, `GET/POST /api/settings/smtp/test`,
    `POST /api/settings/secret/clear`, `POST /api/ldap/sync`, and notification history/tests.
- **Website/application policy signing no longer gives every endpoint the
  fleet's bundle-forging secret.** Agent 5.1.2 verifies domain-separated
  Ed25519 statements with the server's public active/retired-in-grace key ring;
  the server no longer returns either legacy policy HMAC field, and upgraded
  agents purge cached copies. Invalid, unknown, revoked, expired, tampered, or
  cross-policy signatures preserve the last verified enforcement state. (risk:
  critical — coordinated agent/server trust-protocol change)
  - Migration: publish and roll out agent 5.1.2 before or alongside the server
    change. Older agents safely reject the new algorithm and retain their last
    valid policy, but cannot accept subsequent policy changes until upgraded.
  - Rollback: roll back the coordinated server and agent release. Do not restore
    shared-secret delivery as a compatibility mechanism.
  - Evidence limit: automated tests cover signing, public-key delivery,
    rejection, key lifecycle, and last-good behavior; physical endpoint and
    production fleet validation remain pending.
- **The website policy bundle now rejects a stale-but-validly-signed
  replay.** `apply_proactive_blocks` only deduplicated by content hash — a
  genuinely older, correctly-signed bundle with a lower `version_number` was
  still applied on a hash miss, unlike the AV bundle path, which already
  tracks a durable anti-rollback watermark against this exact threat. It now
  persists and enforces a `website_policy_bundle_min_version` watermark
  (survives restart, mirrors `av_bundle_min_version`); an authorized rollback
  is still re-published as a new forward version and is not rejected. (risk:
  medium — closes a policy-downgrade replay window; found by this release's
  review gate)
  - **Not applied to the application policy bundle**, on second review: its
    `version_number` (`server/main.py: _get_agent_signed_application_bundle`)
    is derived from a content hash, not a monotonic counter — a min-version
    watermark there would risk permanently rejecting a legitimate future
    policy change whose hash happens to sort lower. Needs a genuinely
    monotonic version source server-side (mirroring
    `WebsitePolicyBundleVersion`) before this protection can be added safely;
    tracked as follow-up, not fixed in this release.
- **"Deploy" no longer claims endpoints it never reached.**
  `POST /api/updates/{id}/deploy` queues nothing — it stamped the package row and
  returned however many agents happened to be online, which the Updates screen
  printed as "Deployed to N agents". That was merely generous while the agent's
  own poll served the newest package to whoever asked; once that poll moved
  behind a release campaign (see the staged-release-governance entry above), the
  number of endpoints a click actually reaches is zero until a campaign or ring
  pin exists — and the toast became simply false, with the refusal reaching the
  wire but no screen. `deploy` now reports `released_to_agents` alongside the
  stamp and `requires_campaign` when endpoints exist but none can receive the
  package; `/api/updates/summary` carries the same coverage block, so the page
  can distinguish "behind" from "unreachable"; and the confirmation says what the
  click will do. The default-deny policy itself is unchanged — this makes it
  visible instead of letting the product claim otherwise. (risk: medium — no
  policy change; corrects a false success report and surfaces the gate)
- **A failed first install no longer rolls the deployment onto a placeholder.**
  `.env.prod.example` ships `AXELOOT_IMAGE=…@sha256:REPLACE_WITH_APPROVED_DIGEST`,
  and `update.sh` treated that non-empty value as a real pin — so a first boot
  that failed its health gate was "rolled back" onto an image that does not
  exist, turning a failed install into a stack that cannot start at all.
- **`keys` is excluded from the Docker build context.** First-run setup writes
  private agent-trust signing material to `<repo root>/keys/agent_trust`, and
  nothing shipped it only because the Dockerfile copies `server/` rather than the
  repo root — an accident of one default path, not a defence. A test now asserts
  the secret-bearing paths stay out of the build context.
- **`test_failover_then_primary_recovery` passed or failed on host uptime.** It
  wrote a literal `0` into `_last_primary_retry` to mean "the retry cooldown has
  elapsed", but `endpoints_for_request()` compares that against
  `time.monotonic()`, whose reference point is undefined (seconds since boot on
  Linux) — so the assertion only held once the machine had been up longer than
  `PRIMARY_RETRY_SECONDS`. On a container started more recently the test failed
  for a reason unrelated to failover. Now expressed against the same clock; the
  guard was mutation-tested to confirm it still catches the real behaviour.
- **The Windows agent's update check was silently failing on every
  fingerprint-enrolled endpoint.** `AgentUpdater._headers()` sent only
  `X-Agent-Key`, which the server rejects wherever the agent row carries a
  `hw_fingerprint` — every enrolled agent — so `/api/updates/latest/{os}` and
  the package download endpoint answered 401 on every check; the failure was
  swallowed and read on the endpoint as "up to date". Both call sites now
  share the same `APIClient.auth_headers()` builder the telemetry path already
  used correctly. (risk: high — silent update-discovery failure)
  - Evidence limit: does not recover already-deployed agents on the broken
    version — they cannot fetch this fix through the path it repairs and must
    be reached through the command channel instead, same shape as O48.
- **A rejected sign-in left no audit record, and the one row that did survive
  named the actor `"system"`.** Every login-failure branch raised before
  commit, so its audit row rolled back with it — account-not-found, disabled,
  and locked-out attempts recorded nothing at all; only the wrong-password
  branch survived, by accident, riding along on an unrelated commit. Failures
  now commit through `record_auth_event` on a session of its own, and the
  actor is the claimed username (never `"system"`) when the server never
  resolved an account, with `user_id` left NULL as the signal that the
  identity was never verified. (risk: high — closes an audit-integrity gap for
  exactly the two events these rows exist to evidence: credential spraying and
  account enumeration)
  - Migration: none. The audit actor field is now clamped to its DB column
    width so an over-long claimed username cannot fail inside the audit
    transaction on PostgreSQL.
- **Static assets shared the API rate-limit zone, so a normal page load could
  503 its own CSS/JS.** `deploy/nginx.conf` had no dedicated `/static/`
  location, so the ~61 same-origin resources one authenticated page load
  fetches fell through the catch-all API zone (rate=20r/s, burst=40) and
  16-17 of them came back 503 — a CSS `@import` failing silently on a
  non-2xx response reproduces exactly the "sidebar fine, shared content
  degraded, refresh sometimes fixes it" symptom this reopened (O30/O51).
  Static assets now get their own zone (burst=400, sized against measured
  1x/3x/5x concurrent-page-load NAT/proxy concurrency); a new governed
  `deploy/linux/update-nginx.sh`, run by `upgrade.sh` only after the app
  upgrade already reports healthy, re-renders and reloads the config on
  existing single-host installs (validates with `nginx -t`, backs up and
  rolls back on failure). (risk: medium — deployment/availability fix; the
  API zone's own rate/burst is unchanged everywhere else)
  - Evidence limit: authenticated-browser reproduction on the live host
    remains blocked (no owner credentials available in-session); the failure
    and fix were validated against equivalent unauthenticated real-nginx
    instances plus a rendered-config regression test. Owner validation of the
    authenticated Overview after deploy remains the final confirmation step.

### Changed
- **`deploy/bootstrap.sh` and `scripts/build-offline-bundle.sh` are retired** and
  now refuse to run, each naming its replacement. Neither could produce a working
  install against the current deployment contract: `bootstrap.sh` wrote no
  `AXELOOT_IMAGE` and created none of `config/app.env`, the file-based secrets or
  the PostgreSQL TLS material, and the offline bundler omitted `deploy/linux/`,
  without which PostgreSQL and Redis cannot start on the receiving host.
  (risk: medium — a documented command now exits non-zero, deliberately, rather
  than producing a directory that looks installed and a stack that cannot start)
- **`docs/GETTING_STARTED.md` rewritten** around the bundle + `deploy/linux/`
  path. It had been pointing at a DNS name that does not resolve
  (`get.axeloot.com`), a renamed compose service (`logs server` → `app`), two
  scripts that are not installed at those paths, and it omitted
  `AXELOOT_PUBLIC_HOST` and the public TLS cert/key that `validate-config.sh`
  stops on.
- Bundles are now named after the **image they contain** rather than the checkout
  that packed them, and `BUNDLE.txt` records `kit_version` alongside
  `axeloot_version` so mixed provenance is visible instead of contradictory.
- **UAM behavioral risk is now a bounded default-on advisory capability.** Adds
  explicit disabled/advisory/authoritative modes, cached API/UI confidence,
  coverage, freshness, reasons, provenance, and a fail-closed authoritative
  cutover boundary. Free-form Settings JSON cannot authorize cutover;
  authoritative requests resolve to advisory until a future governed
  real-world evidence path exists and is owner-approved. `weighted_v1`
  remains authoritative and advisory output cannot create
  alerts, incidents, actions, enforcement, or proof. (risk: high)
  - Rollback: set `uam_behavioral_risk_mode=disabled`; additive cache columns
    remain safe to ignore.
  - Evidence limit: automated tests validate code contracts only. No legitimate
    labeled corpus, runtime deployment, or real-world efficacy proof is claimed.

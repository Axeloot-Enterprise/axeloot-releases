### Security
- **Auto-trigger playbook conditions were never persisted (S1).**
  `PlaybookRequest` accepted and validated `conditions`, the column existed and
  a migration created it, but neither POST nor PUT ever assigned it — so every
  playbook stored `[]`, and `evaluate_conditions([], …)` returns `(True, [])`.
  An operator's *"only when severity is critical"* did not exist at runtime and
  the playbook fired on **every** matching alert, on response paths whose steps
  include `isolate_host`. Nine columns were affected, not the six originally
  filed. (risk: critical)
  - Affected: every deployment since playbook auto-trigger shipped; any playbook
    saved with conditions.
  - Mitigation: conditions are persisted and evaluated. The wizard and the
    engine previously shared **zero** condition fields and two of eight
    operators; both now use one vocabulary, so a stored condition means what
    the wizard showed.
  - Rollback: reverting restores unconditional firing — prefer disabling the
    affected playbooks over rolling back.
- **Scoped UAM application rules were enforced fleet-wide.** The rule-targeting
  pickers persist scope into the `UAMPolicy.applies_to_*` columns, but the
  signed application (executable-block) bundle gated on `conditions["scope"]`,
  a key the picker never writes — an empty dict matched every agent. A
  user/device/department-scoped BLOCK rule was delivered to, and enforced on,
  endpoints explicitly outside its scope. The website delivery path was
  corrected earlier in this window; this closes the application half.
  (risk: high)
  - Affected: v5.6.0–v5.6.1 and any dev build before this release, for any UAM
    application rule scoped narrower than "all users".
  - Mitigation: bundle delivery, the admin enforcement preview and agent drift
    reconciliation now share one scope gate. An empty scoped target never
    expands to the fleet, and an unresolvable picker reference drops the rule
    rather than broadening it.
  - Rollback: reverting restores fleet-wide enforcement of scoped rules —
    prefer disabling scoped block rules over rolling back.
- **UAM built-in rule safety restored** and website delivery evidence
  preserved; UAM rule-processing transactions now recover safely; single-org
  security boundaries enforced. (risk: high)
- **Single-leader retry-queue draining enforced** (DBSEC-006). (risk: medium)

### Performance
Driven by a production HAR capture from the deployed box rather than by reading
code, ranked twice — by `timings.wait` (server cost) and `timings.blocked`
(browser queueing), which answer different questions.

- **`/api/dashboard/productivity`: 44.3 s of server time on one page load.** The
  endpoint had no cache at all — `TTL_PRODUCTIVITY = 30` was declared in
  `analytics/cache.py` and never used — and grouped on a JSON expression rather
  than an indexed column. Now cached and grouped on indexed columns:
  10.29 s → 0.00 s cached over 300k rows. (risk: medium)
  - Migration: none required.
- **The demo/validation exclusion filter cost more than any single query.**
  Excluding demo/smoke/validation rows scanned five columns for twelve tokens on
  every row of every aggregate — 60 leading-wildcard `LIKE`s per row from 12
  call sites — and was the shared cost under `soc-summary` (5.7 s),
  `ops/status` (5.0 s) and `admin/diagnostics` (4.4 s). That answer cannot
  change after a row is written, so it is now written down at insert:
  telemetry stamps it at its single ingest site, `Alert` via a mapper hook
  because it is constructed in 14 places across 8 modules and a missed call
  site would default to `False` — seeded data silently counted as production.
  1328 ms → 283 ms over 300k rows, identical results. (risk: medium)
  - Migration: applied automatically by the versioned migrator on startup.
- **65 static requests carried 51 s of cumulative queueing — mean 786 ms each —
  time the server never saw.** Every request was HTTP/1.1, so the browser's
  six-connections-per-host limit serialised ~25 JS files plus CSS.
  `deploy/nginx.conf` said `listen 443 ssl http2`, a form deprecated and
  ignored since nginx 1.25.1 — exactly how a config reading "http2" serves
  HTTP/1.1. Switched to the separate `http2 on;` directive; versioned assets
  are now served immutably. (risk: medium)
  - Migration: **operators must redeploy `deploy/nginx.conf`.** Verify with
    `curl -sI --http2 https://<host>/`.
- **Overview and Incidents fetched everything twice per load.** Overview issued
  24 API requests where 18 were needed (the whole phase set duplicated);
  Incidents 11 where 10 were needed; `soc-summary` was separately fetched twice
  per page load. (risk: low)

### Known limitations

- **`manager` and `auditor` roles can read individual employees' browsing
  history.** Three per-user UAM detail routes
  (`/api/users/monitored/{username}/activity`, `.../alerts`, `.../sites`)
  are gated on the `uam.data.read` permission rather than the narrower
  `users.monitored.view`. `uam.data.read` is held by `manager` and `auditor`
  in addition to `admin`/`analyst`, and these routes return full activity and
  alert **content**, not just the usernames, hostnames, risk scores and
  timestamps the UAM *list* endpoints return. There is no department or
  ownership scoping on them, so a `manager` can read any monitored user, not
  only their own reports.

  If that is wider than your deployment's privacy posture allows, restrict
  `manager`/`auditor` role assignment accordingly until this is scoped. This
  is under review and expected to change in a future release.

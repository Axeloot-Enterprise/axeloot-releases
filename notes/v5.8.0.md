
### Added
- **Default-off tenant-scoped UAM behavioral-risk candidate.** Adds a centralized
  deterministic feature contract, prior-only 7-day fast/30-day stable self and
  eligible department-peer robust baselines, novelty/deviation findings,
  confidence/coverage, recency decay, bounded journey-cache materialization,
  aggregate-only API/UI explanation, and a read-only chronological same-corpus
  legacy comparison tool. The existing `weighted_v1` score remains authoritative:
  no legitimate labeled corpus was available, so measured efficacy and cutover
  are explicitly pending. (risk: high)
  - Migration: three additive v13.4 `user_journey_cache` columns; candidate
    execution defaults off via `uam_behavioral_risk_shadow_enabled=false`.
  - Rollback: disable the setting and ignore the nullable candidate columns;
    schema removal requires an approved forward fix or verified restore.
  - Evidence limit: automated tests prove deterministic code behavior and
    leakage/tenant/privacy boundaries, not real-world detection efficacy.
- **Smart Windows Deployment v1 and Windows agent 5.1.1 source contracts.**
  Assets now defaults to scoped, expiring, use-limited deployment links with a
  one-time fragment secret, isolated no-store/no-referrer landing exchange,
  signed deployment profiles, device-bound one-time enrollment grants, and real
  server-derived registration/heartbeat completion. The Smart Installer verifies
  profile/TLS/SPKI/package signature/size/SHA-256, installs a real per-machine
  WiX MSI, validates `SecWorker`, and rolls back with bounded failure codes.
  Enterprise bundles use a profile path rather than a raw token and expose the
  actual built MSI ProductCode. Raw-token deployment remains collapsed under
  Advanced troubleshooting. Release tooling builds the agent, desktop, Smart
  Installer, MSI, metadata, checksums, and install detection from isolated native
  Windows Python 3.12, and gates on the offline packaged self-test. (risk: high)
  - Migration: publish new 5.1.1 artifacts; do not rename or overwrite historical
    5.1.0 evidence. Existing identities are preserved under ProgramData.
  - Rollback: disable deployment links, stop distribution, and uninstall using
    the actual ProductCode; restore only a previously approved package.
  - Evidence limit: source-level local tests pass only after the commands cited
    in the PR. Native clean-Windows, Authenticode, real service/enrollment, and
    heartbeat evidence remain mandatory before any production-readiness claim.
- **Durable UAM session graph.** Correlates Windows session lifecycle events
  (logon / rdp_disconnect / rdp_reconnect / logoff) into a tenant-scoped,
  native-session-keyed session graph instead of treating each event in
  isolation. Identity resolution only accepts authoritative or qualified input
  (SID, directory object id, UPN, or domain-qualified account name) and
  excludes workforce service accounts; event-to-session linking is bounded and
  leaves ambiguous matches unassigned rather than guessing. Includes an agent
  fix to normalize Windows event-log timestamps to UTC and a stabilized
  Windows boot-generation key, both prerequisites for correct session
  correlation. (risk: medium)
  - Migration: additive `UAMUserSession` / `UAMSessionEventLink` tables.
  - Rollback: tables are additive and unread by other code paths; safe to
    ignore or drop.
  - Evidence limit: automated tests cover lifecycle correlation and
    out-of-order event handling; no production endpoint-fleet validation yet.
- **One-click Smart Deployment UX and reliable package download.** The admin
  Deploy Agent flow now defaults to zero-input Create Installation Link /
  Download Installer, with device identity, enrollment, and the internal
  bounded-fleet/single-use mechanics handled automatically and never surfaced
  in the normal UI; the raw-token workflow moves under a secondary Advanced
  disclosure. Fixes a package-download reliability gap found via a real
  endpoint test: the Smart Installer's download loop now categorizes every
  connect/stream fault into a distinct `package_download_failed` (32) exit
  code (kept separate from hash-mismatch integrity failures), retries
  transient faults up to 3 times on the same still-valid enrollment grant, and
  always terminates through one bounded, human-readable result instead of
  failing silently. Adds an admin-authenticated smart-bundle download endpoint
  so "Download Installer" produces the identical bundle the public
  installation link serves, and deployment status now shows a real
  bound-endpoint hostname instead of raw internal target fields. (risk: medium)
  - Migration: none required.
  - Rollback: raw-token deployment remains available under Advanced.

- **The session graph silently discarded out-of-order logoffs.** A logoff whose
  event time was older than `last_seen_at` — ordinary with batched telemetry —
  was dropped, so the session kept a non-terminal state until `_STALE_AFTER`
  aged it out, and the observed termination was lost entirely. Reworked on
  event-time authority, with an explicit founder decision that
  `ended_at < last_seen_at` is allowed: the two answer different questions
  ("when did it end" vs "the last thing we saw"), and discarding real evidence
  is the worse failure in a security product — activity after a logoff is a
  signal to surface, not smooth away. `last_seen_at` stays a monotonic
  high-water mark, `lifecycle_state` follows the latest event by event time,
  and `ended_at` keeps the earliest observed termination so a duplicate cannot
  push the boundary outwards. The projection is now commutative: replaying a
  session's events in any order lands on the same row, which is asserted over
  every permutation of a logon/disconnect/logoff sequence. (risk: medium)

### Security
- **Agent connectivity refresh is now actually signed, and the agent refuses an
  unsigned one.** The `config_refresh` envelope carries `server_url` and
  `tls_verify`, but the server emitted `"signature": None` on every payload and
  the agent's verifier returned *true* when no signature was present — so the
  replay, expiry and nonce guards around it were protecting a payload nobody
  authenticated. Anyone able to modify a single HTTP response could repoint an
  agent at their own server or switch off certificate validation, and the
  change persisted after they lost that position. Worse, the bare
  `{server_url, tls_verify}` shape the server still emits for older agents
  bypassed the envelope entirely, so stripping `config_refresh` was enough.
  The server now Ed25519-signs the envelope with the agent-trust key (the same
  mechanism trust-recovery commands already used), and the agent fails closed:
  no signature, no `key_id`, an unknown key, a bad signature, or the unsigned
  flat shape are all rejected. (risk: critical)
  - Affected: every release before this one; the flaw is live in production,
    not introduced this window. It was found by this release's review gate
    while auditing code that predates the window.
  - Migration: none. The server signs first and older agents already verify a
    signature when one is present, so a signed payload is accepted by both old
    and new agents; upgrade order does not matter.
  - Rollback: reverting restores a silently forgeable connectivity channel —
    prefer rolling forward.
  - Evidence limit: covered by tests on both sides, including the exact
    canonicalization contract between them, plus forged-key, tampered-field and
    stripped-envelope cases. No live MITM exercise was performed.
- **A logged-in console user could bypass licensed-module gating with one
  header.** `ModuleGateMiddleware` skipped the disabled-module 403 whenever an
  `X-Agent-Key` header was present, and never validated it — so any operator
  with a session could add the header to their own authenticated request and
  reach a module the licence disables. Agent ingestion legitimately posts to
  module-owned prefixes, so the exemption stays, but a request carrying user
  credentials (bearer token or session cookie) is no longer treated as agent
  traffic. A forged header without credentials still reaches nothing — it
  skips *licensing* only, and the route's own agent authentication rejects it.
  (risk: medium — pre-existing, not introduced this window.)
  - Migration: none required.
  - Rollback: none required — restores the bypass.
- **SSO admins in a pre-rebrand IdP group were silently demoted to viewer.**
  The EXMonitor→Axeloot rebrand replaced `"exmonitor admins"` in
  `DEFAULT_ROLE_MAPPING` with a second copy of `"axeloot admins"` rather than
  renaming it, so the dict carried one key twice and lost the legacy mapping
  entirely. Any deployment whose directory group was never renamed dropped its
  admins to `default_role` on their next SSO login. Restored, and kept: the
  project's stated policy is that pre-rebrand names keep working, and customers
  do not rename directory groups on our release schedule. (risk: medium —
  pre-existing, not introduced this window.)
  - Migration: none required.
  - Rollback: none required.
- **UAM watchlist reads and writes were not tenant-scoped** (found by
  external Codex review, verified and fixed). `UamWatchlistEntry` carries a
  `tenant_id` column, but the list/add/remove routes and the row lookups they
  share never filtered or set it, and the model was missing from
  `tenancy._tenant_owned_models()`. Not currently reachable — the product
  enforces single-tenant mode — but a real latent cross-tenant read/write the
  moment multi-tenancy is enabled, and inconsistent with the rest of this
  window's UAM work, which was otherwise careful about this exact pattern.
  Fixed the three direct API routes; the two analytics call sites that feed
  `_active_watchlist_map` from an already-tenant-unaware discovered-users
  pipeline are a larger, pre-existing gap (tracked separately — see
  `CLAUDE.md`'s "Identity separation" item) and were not touched here.
  (risk: medium)
  - Migration: none required.
  - Rollback: none required — pre-existing broken behavior, not a regression
    to revert to.
- **`X-Forwarded-For` was read from the left, so a client could choose its own
  identity.** `deploy/nginx.conf` forwards `$proxy_add_x_forwarded_for`, which
  preserves whatever the client sent and appends the address nginx actually saw.
  `_get_real_ip` took the **leftmost** entry, so a request carrying
  `X-Forwarded-For: 1.2.3.4` was attributed to `1.2.3.4` in rate limiting, logs
  and audit. The chain is now read right-to-left, skipping entries that are
  themselves trusted proxies, so a legitimate CDN → nginx chain still resolves
  while a client-supplied prefix is ignored. Raised as a P1 against the CIDR fix
  below, which would otherwise have activated this latent flaw on every host
  running the shipped `TRUSTED_PROXY_IPS=172.16.0.0/12` default.

- **systemd never took ownership of the stack, so `systemctl stop` did nothing.**
  `install.sh` ran `systemctl enable axeloot.service` but never started it, while
  bringing the stack up with compose directly. The unit therefore sat at
  `inactive (dead)` — journal empty — while the application served traffic, and
  `systemctl stop axeloot` exited **0 without stopping anything**: an operator
  taking the service down for maintenance would not have. Changed to
  `enable --now`; `stack.sh start` is idempotent, so it adopts the running stack.
  Verified afterwards that stop really stops and start returns the stack to
  healthy in ~19s — the boot path, exercised without a reboot.
- **Agent-trust key management was broken on every containerised install.**
  `docker-compose.prod.yml` set `AXELOOT_KEYS_DIR`, which nothing in the server
  reads — `key_management.py:41` reads `AXELOOT_AGENT_TRUST_KEY_DIR`. The store
  therefore fell back to `BASE_DIR/keys` (`/app/keys`) on the read-only rootfs,
  so `peek_active_key_id` failed with `Errno 30` and, because AV bundle signing
  now goes through that key registry rather than the old symmetric setting, the
  publisher refused every bundle: `BundleSigningUnavailable: No active AV bundle
  signing key available`. Pointed the variable at the mounted directory and made
  that mount writable — the registry and first active key are created on demand,
  so a fresh install cannot use a read-only mount.
- **`scripts/setup_signing_keys.py` could not run in a container.** It aborts
  with `ERROR: .env not found` unless a `.env` file exists, even though it
  already falls back to `os.environ` for `DATABASE_URL` — so the documented
  signing-key setup step was impossible on the supported Docker deployment. It
  now proceeds when `DATABASE_URL` is in the environment.
- **Every kit-built image reported its own provenance as invalid.**
  `deploy/Dockerfile` writes `artifact_version` (the approved image reference)
  into `/app/BUILD_METADATA.json`, and `LINUX_SINGLE_HOST_DEPLOYMENT.md`
  documents it as part of the build record — but `_ALLOWED_FILE_FIELDS` in
  `server/versioning/build_metadata.py` did not list it, so the strict schema
  check flagged it as unknown and `/api/version` returned
  `"status":"invalid","invalid_fields":["metadata_schema"]` on every build.
- **Three certificate checks in the Linux kit were reading the wrong signal.**
  `openssl x509 -checkhost` prints `does match` / `does NOT match` on stdout and
  exits **0 either way**, but the kit branched on its exit status. So
  `validate-runtime.sh`'s "the DB certificate must not validate 127.0.0.1"
  guard fired unconditionally and no install could ever finish, while
  `validate-config.sh`'s two "must match" guards — the Postgres SAN and the
  public TLS hostname — never fired at all and would have passed a certificate
  for the wrong host. Added `cert_matches_host` / `cert_matches_ip` helpers in
  `common.sh` that read the verdict, and switched all three call sites to them.
- **The application could not start on the read-only root filesystem.**
  `docker-compose.prod.yml` mounted the writable `app_logs` volume at
  `/app/server/logs`, but `server/main.py` derives `BASE_DIR` as
  `Path(__file__).parent.parent` — `/app` — and creates `/app/logs` at import
  time. With `read_only: true` that is an immediate
  `OSError: [Errno 30] Read-only file system: '/app/logs'`, before any startup
  check runs. Moved the mount to the path the code actually uses.
- **The application container could not read any of its own secrets.**
  `deploy/Dockerfile` runs the app as `axeloot` uid/gid **10001**, while
  `bootstrap-host.sh` created the host `axeloot` account with whatever id
  `useradd --system` picked (995/986 on a stock Ubuntu 24.04). Compose
  file-secrets are bind-mounted with host ownership intact, so the 0600 files
  `validate-config.sh` requires were owned by a uid that does not exist in the
  container:
  `axeloot-container-entrypoint: cannot open /run/secrets/postgres_password:
  Permission denied`. Bootstrap now pins the host identity to 10001 and refuses
  to continue if an existing account has different ids.
- **Redis could never start under the Linux deployment kit.**
  `deploy/linux/redis-entrypoint.sh` writes `redis.conf` and `users.acl` as root
  under `umask 077` into `/run/axeloot`, a tmpfs mounted `mode=0700`. The base
  image's entrypoint then re-execs `redis-server` through `gosu` as the
  unprivileged `redis` user, which cannot read either file:
  `Fatal error, can't open config file '/run/axeloot/redis.conf': Permission
  denied`. The container restart-looped and `install.sh` failed at
  `wait_healthy redis`. The entrypoint now hands the directory and both files to
  `redis` before exec.
- **`deploy/linux/install.sh` silently disabled HTTP/2 on nginx ≥ 1.25.1.** The
  template renders `listen 443 ssl http2;`, which those builds ignore in favour
  of the standalone `http2 on;` directive. Install now detects the nginx version
  and renders the form that build honours. This is the regression
  `deploy/nginx.conf` was previously fixed for; a production capture measured
  51 s of cumulative request queueing when the console fell back to HTTP/1.1.
